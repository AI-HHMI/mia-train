# How much of NISB `base` does a model actually need?

The benchmark's own baselines show 100 cubes doing no better than 5, which says the *upper* end of
NISB's data curve is flat. That is why the pseudo-labelling experiment could not answer the
question it was built for: on a procedurally generated dataset, "more data" stops adding
information at some point, and nothing downstream can recover what the generator never varied.

This asks where the flat part starts. Three arms, nested subsets of `base`'s five training cubes:

| arm | cubes | training data |
|---|---|---|
| 1 | 1 | `seed0` |
| 3 | 3 | `seed0,1,2` |
| 5 | 5 | `seed0,1,2,3,4` |

If 1 == 3 == 5, the saturation point is at or below one cube and NISB's label budget was never the
binding constraint. If 5 > 3 > 1, the curve is still rising at five and the 100-cube null is about
`train_100`'s *diversity* rather than about volume. Either answer is worth having before leaving
the dataset, and neither is available from any run done so far.

**Pure supervised finetuning. No SSL, no pseudo-labels.** The point of comparison is a pretrained
checkpoint plus labels, which is the baseline every SSL result here eventually has to beat.

## Arms differ in two lines and nothing else

The six configs are generated by `make_configs.py` rather than hand-maintained, because six
near-identical TOMLs is exactly how "the arms are identical" quietly stops being true. Verify it:

    diff <(grep -v '^#' 1a_interp.toml) <(grep -v '^#' 5a_interp.toml)

which prints `experiment_name` and the data `config_path`, and nothing more. Regenerate after any
edit to the template and read the `git diff`.

Cubes are taken in seed order, so the arms are *nested* — a difference between them cannot be a
difference of which cubes were drawn. It can still be a difference of which cube is `seed0`: the
1-cube arm rests on one volume, and n=1. Read a null there as "one cube was enough"; read a large
deficit as "this cube was not enough" and re-run against `seed3` before generalising.

## Two stages, because the architecture requires it

    stage A   released DINOv3 ViT-L/16, inflated 2D->3D   interpolating decoder   200k steps
    stage B   stage A's own encoder (prefix = "model.")   sub-pixel decoder       100k steps

Stage B is not a schedule choice. A sub-pixel head has never trained from a cold encoder in this
repo — three attempts all collapsed onto the trivial "everything is connected" predictor
(`init_comparison/README.md`) — so stage A exists to hand stage B a trained encoder. Each arm
warm-starts from *its own* stage A, which is what keeps the 1-cube number from being contaminated
by an encoder that saw five.

Stage A stops at 200k rather than `banis_parity`'s 300k because 200k is the checkpoint that lineage
actually went on to use.

## Optimisation

Peak LR 3e-4, `min_lr_ratio = 0.001`, linear schedule, 2000 warm-up steps, weight decay 0.05,
grad-clip 1.0, `layerwise_lr_decay = 1.0`, `patch_embed_lr_mult = 1.0`, `drop_path_rate = 0.1`,
bf16, batch 1 per rank x 8 ranks = global batch 8. As in `pseudo_labeling`.

Two of those are load-bearing and were paid for:

- **`warmup_steps = 2000`.** At 500 both pseudo-labelling arms collapsed onto the trivial
  predictor, visible as `affinity_accuracy` converging on `target_positive_rate`.
- **`layerwise_lr_decay = 1.0` and `patch_embed_lr_mult = 1.0`.** The 0.9 x 0.2 combination put
  `patch_embed`'s effective LR 696x below BANIS', which froze the stem and scored 2.6% nERL.

Augmentation is BANIS' defaults, held identical across arms. It matters more here than usual: with
one cube, augmentation is most of what stands between the run and memorising a single volume. That
also means it is a confound if tuned per arm, so it is not.

## Running it

    bash experiments/data_scaling/submit.sh              # all three arms, both stages
    bash experiments/data_scaling/submit.sh --dry-run    # print the bsub lines, submit nothing
    bash experiments/data_scaling/submit.sh --smoke      # 20 steps of every stage, one GPU
    bash experiments/data_scaling/submit.sh 5            # one arm

One full node per arm, one queue per arm — arms 1 and 3 on `gpu_h100`, arm 5 on `gpu_h200`, which
is the 2x H100 + 1x H200 that were free at submission. Deliberately *not* the twin-queue pattern
the earlier experiments used: those wanted whichever generation freed up first, whereas here the
allocation *is* the pinning. Override with `ARM_QUEUE_5=gpu_h100`. H100 and H200 differ in
throughput, not arithmetic, so which arm lands where changes when a number arrives, never what it
is.

Stage B is submitted at the same time as stage A, held on `-w done(A)`. It cannot name its
predecessor's checkpoint at submission — the run directory does not exist yet — so it carries a
`PREV_CHECKPOINT` placeholder and resolves it in-job, picking the highest step numerically
(`sort -n`; plain `sort` puts `step_90000` after `step_200000`) and asserting it reached 200k.

**Wall clock.** 34 h for stage A, 20 h for stage B. Measured in flight on 2026-08-21: 30.9 / 27.9
samples/s on H100 and 32.0 on H200 at global batch 8, i.e. ~0.26 s/step, so stage A runs ~14.5 h and
stage B (sub-pixel, somewhat heavier) under ~10 h. The requested walls are therefore ~2.3x the
estimate rather than the 1.5x intended -- kept deliberately, because it costs nothing and a
wall-clock kill at step 190k costs 14 h -- and `-W` overruns do *not* requeue even with `-r`. If
stage A does get killed, `done(A)` never fires, LSF drops stage B, and recovery is
`submit.sh <arm>` again — both stages pass `--resume`, so stage A continues from its last
checkpoint rather than restarting.

Checkpoints every 20k (stage A) and 10k (stage B): 10 per stage, ~4.8 GB each, ~290 GB for the
whole experiment.

## Reading the result

`val/boundary_accuracy` is what these runs log and is fine for watching a run train. Ranking the
arms is a separate step: `score.sh` predicts affinities over the **whole** `seed100` cube and scores
nERL through the BANIS path (`mia_predict.py` then `mia_score.py`).

    bash experiments/data_scaling/score.sh              # final stage-B checkpoint of each arm
    bash experiments/data_scaling/score.sh --stage a    # stage A instead

Whole cube rather than a block, so every arm is measured over the same extent. Two consequences to
keep straight: nERL is **not** comparable across extents -- the same model scored 0.3045 whole cube
and 0.4192 on a 512^3 block -- so these numbers compare to each other and to the whole-cube
`init_comparison` figures, but **not** to `subpixel_decoder`'s 0.5844, which is a block figure.
And `--patch 256` is not a knob: RoPE normalises coordinates by the runtime grid extent, so any
other patch size silently changes every position the encoder sees.

Each whole-cube prediction is ~51 GB, so the scoring job deletes the affinities once its JSON is
written.

## Results (2026-08-22)

All six stages ran to their full step counts. Final stage-B checkpoints (step 100k) scored on whole
cubes with `score.sh`.

| arm | `base` seed100 nERL | `slice_perturbed` seed107 nERL | retained | val boundary acc |
|---|---|---|---|---|
| 1 cube  | 0.4226 | **0.0816** | **19.3%** | 0.9217 |
| 3 cubes | **0.4311** | 0.0755 | 17.5% | **0.9228** |
| 5 cubes | 0.3906 | 0.0650 | 16.6% | 0.9183 |

**More labelled cubes bought nothing, in distribution or out of it.** On `base` the arms span
0.391-0.431, and the ordering is 3 > 1 > 5 -- not monotone, and 5 cubes is the *worst*. On
`slice_perturbed` the ordering is strictly 1 > 3 > 5, and the retained fraction falls monotonically
19.3% -> 17.5% -> 16.6%. Three independent measurements (val boundary accuracy, `base` nERL,
`slice_perturbed` nERL) all place the 5-cube arm last.

**There is no overfitting to explain it away.** Train boundary accuracy was 0.9058 / 0.9062 / 0.9070
across the arms -- identical -- and *below* val (0.9217 / 0.9228 / 0.9183), because train is
augmented and val is not. The 1-cube arm is not memorising its single volume; one cube of NISB
`base` simply spans what five cubes span. That is a stronger claim than the benchmark authors'
100-vs-5 null, and it is the reason to stop using NISB to test data-quantity or SSL hypotheses.

Caveat on effect size: n=1 per arm, and the 0.39-0.43 spread on `base` is the same order as the
differences being read. Treat "5 cubes is worst" as unresolved between a real effect and run-to-run
noise; treat "more cubes does not help" as established, since it is the one statement all three
metrics agree on.

### The `slice_perturbed` probe measures augmentation coverage, not data quantity

`slice_perturbed` is brutally harder for every arm -- nERL 0.065-0.082 against 0.391-0.431, a ~5x
drop -- and the failure is almost entirely fragmentation: 34k-37k splits against ~4k on `base`,
with `voi_split` rising 1.64 -> 4.0-4.4 while `voi_merge` barely moves.

Measured on seed107 (a 256x256 column, all 1350 sections): **10.4% of sections are completely
blank** -- 143 of 1350 have exactly zero contrast -- against 0 of 1350 in seed100. Per-section mean
intensity varies 8.4x more (sd 45.9 vs 5.5), with adjacent-section jumps up to 176 grey levels
against 17.

That is the same *mechanism* `src/data/augment.py:drop_sections` implements -- it blanks sections to
0.0 -- so this is not an unseen corruption. But the arms trained at `drop_slice_prob = 0.05` behind
a 50% coin, and along a **randomly chosen one of the three spatial axes**, so only about a third of
the applied drops ran along the sectioning axis at all. Against a cube where 10.4% of z-sections are
always gone, that is roughly an order of magnitude of under-exposure.

So the honest reading of this column is that it tests whether the *augmentation* covers section loss,
and no quantity of `base` cubes contains section loss to learn it from. If section-loss robustness
is wanted, the lever is `drop_slice_prob` and restricting the drop axis to the sectioning axis --
not more cubes.
